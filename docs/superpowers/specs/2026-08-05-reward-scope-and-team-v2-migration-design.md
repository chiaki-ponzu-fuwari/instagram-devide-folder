# 報酬範囲切替と既存チームV2移行 設計

## 目的

個人報酬ページの対象範囲を短く読みやすい二択へ変更する。同時に、公開前環境に残る旧形式チームを、Phase 1で導入した安全なFirestore構造へ一括移行し、一般メンバーの利用を再開できる状態にする。

## 確定した画面仕様

- 個人報酬ページ上部の切替文言を、左「個人の報酬」、右「チーム報酬も含む」にする。
- 二つのタブは同じコンテナ内で左右50%ずつとし、端末幅にかかわらず同じ幅にする。
- 既存の保存値 `personalRewardAnalysisScope` と集計ロジックは変更しない。
- 左は個人案件だけ、右は個人案件とログイン中ユーザー本人へ割り当てられたチーム報酬だけを集計する。他メンバー分は含めない。
- 報酬カード、グリッド、余白、ナビゲーションなど、切替以外の既存配置は変更しない。
- 既存の同期中、キャッシュ利用中、一部未同期の状態表示は維持する。

## 移行方式

アプリ画面には移行機能を常設せず、公開前の開発作業でだけ使う一時的なNode.jsスクリプトを追加する。スクリプトはFirebase Admin SDKとGoogle Application Default Credentialsを使い、秘密鍵やアクセストークンをリポジトリへ保存しない。

実行モードは次の二つとする。

- `--dry-run`: 対象チーム、入力文書数、出力予定文書数、検証結果だけを表示し、Firestoreへ書き込まない。
- `--apply`: バックアップを確認した後、チーム単位で移行し、検証に合格したチームだけ利用可能状態へ変更する。

プロジェクトIDはコマンド引数で明示する。Emulator利用時は `FIRESTORE_EMULATOR_HOST` を必須にし、実Firestore利用時はEmulator環境変数がないことと対象プロジェクトIDを二重確認する。本実行はドライラン結果と対象プロジェクトIDを確認した後にだけ行う。

## バックアップ

- 本実行の前に、対象チーム文書と既知の全サブコレクションをJSONへ保存する。
- 保存先は `.migration-backups/<projectId>/<timestamp>/` とし、Git管理対象外にする。
- バックアップにはチームID、文書パス、元データ、取得日時を含める。
- バックアップ作成に失敗した場合は書込みを開始しない。
- Phase 2では旧文書を物理削除しない。必要ならバックアップと旧文書の両方から調査できる状態を保つ。

## チーム単位のデータフロー

1. チームと既知のサブコレクションを読み、バックアップ対象と移行元を固定する。
2. チームの状態が `ready` なら、検証だけを行い、正常なら変更しない。
3. 旧形式または `locked` のチームを `securityMigrationState=migrating` にする。
4. `members/{uid}` から公開可能なプロフィールだけを残し、メールと補足を `memberEmails/{uid}`、`memberNotes/{uid}` へ分離する。
5. 案件、アカウント、フォルダ、テンプレート、表示設定を、パス上のチームID、文書ID、`scope=team`、`schemaVersion=2` を持つ公開文書へ正規化する。
6. 報酬総額、本人配分、経費が旧公開文書へ含まれる場合は、それぞれ `projectRewardTotals`、`projectRewardShares`、`projectCosts` へ分離する。
7. 担当UID、継続親ID、削除情報、revision、作成・更新日時を、既存値がある範囲で保持する。別チームのIDを持つ文書は自動修正せず、そのチームの移行を失敗させる。
8. 書込み後に件数、文書ID、チームID、禁止フィールド、担当UID、継続親子、報酬配分IDを再読込して検証する。
9. 検証成功時だけ `securitySchemaVersion=2` と `securityMigrationState=ready` を同時に保存する。
10. 失敗時は `ready` にせず、再実行できる `locked` または `migrating` のままにする。

## 冪等性と中断対応

- 出力文書IDは移行元IDから決定し、再実行しても同じ文書へ同じ内容を保存する。
- 1回の書込みはFirestoreの上限を超えない小さなバッチへ分割する。
- チームごとの検証が終わるまで一般メンバーのアクセスを許可しない。
- 途中終了後の再実行では、すでに正しいV2文書を再利用し、不足文書だけを補う。
- `ready` チームへ差分がない場合は書込みを行わない。
- 旧文書の削除と、別チームへの文書移動は行わない。

## 権限と安全境界

- 一括移行スクリプトはFirebase Admin SDKを使うためFirestore Rulesを迂回する。代わりに、スクリプト内の事前検証と書込み後検証を必須にする。
- クライアント側のFirestore Rulesは引き続き、一般メンバーを `securitySchemaVersion=2` かつ `securityMigrationState=ready` のチームだけへ許可する。
- 公開文書ではパス上のチームIDと本文の `teamId` が一致しなければならない。
- メール、補足、経費、他メンバーに非公開の報酬は公開文書へ残さない。
- 実Firestoreへの本実行は、対象プロジェクトID、バックアップ完了、ドライラン合格の三条件が揃った場合だけ許可する。

## エラー表示と終了結果

- ドライランと本実行は、チームごとに `skipped`、`ready`、`failed` と理由を表示する。
- 一件でも失敗した場合は終了コードを失敗にし、失敗チームを一覧表示する。
- 本実行後に全チームを再読込し、移行前後の文書数と最終状態をJSONレポートへ保存する。
- データ消失が許容される公開前環境であっても、検証失敗を無視して `ready` にするオプションは用意しない。

## テスト

- 報酬切替の文言、左右均等幅、既存保存値、本人配分限定をNode.jsテストで確認する。
- Firestore Emulatorに旧形式チームを用意し、ドライランが無書込みであることを確認する。
- 通常移行、すでにV2、途中までV2、途中失敗後の再実行を確認する。
- メール、補足、報酬、経費が正しい非公開コレクションへ分離されることを確認する。
- 別チームID、重複ID、不正担当UID、不正継続親、禁止フィールドを検出して `ready` にしないことを確認する。
- Firestore Rulesの全テストを再実行し、移行後は承認メンバーが公開データと許可された履歴を読めることを確認する。
- ブラウザで320、375、390、430pxの切替幅、OFF/ON、同期状態を確認する。
- 実Firestoreではバックアップ、ドライラン、本実行、再ドライランの順に実行し、最後の再ドライランが差分なしになることを確認する。

## 対象外

- アプリ画面への恒久的な移行ボタン。
- 旧文書の物理削除。
- 管理者によるバックアップ復元UI。
- 他チームIDを持つ不正文書の自動付け替え。
- 報酬計算式や、本人配分の対象範囲そのものの変更。
